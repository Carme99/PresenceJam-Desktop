# PresenceJam 3.0 — Research & Implementation Plan

**Date:** 2026-08-09 · **Status:** Research complete, awaiting scope sign-off
**Basis:** 6 parallel research agents (Graph presence APIs, Spotify playback surface, Tauri updater/signing, repo release history, competitor landscape, repo integration points) + direct verification of every load-bearing claim against live Microsoft Learn / developer.spotify.com / tauri.app pages and the v2.10.0 checkout. Every API fact below carries a citation; repo anchors are `file:line` at v2.10.0.

## 1. Executive summary

PresenceJam 2.x is a finished product at its current scope: poll Spotify → set Teams status message, polished across ten minor releases. A 3.0 that is "2.11 with more settings" would be a label bump. The research confirms there is a **real, unclaimed product space** adjacent to the current app, and that most of it needs **no new API permissions at all**:

| Pillar | What it is | New permissions | Competitors |
|---|---|---|---|
| **P1 — Availability sync** | Drive the Teams presence bubble (busy/available) from Spotify state via Graph `setPresence`/`clearPresence` | **None** (docs: delegated `Presence.ReadWrite`, already held) — but a Teams re-consent is still needed to add `profile` (see 3.1) | **None.** No tool writes Teams availability from Spotify. Zapier's "Set Status" is availability-only and still can't write the message |
| **P2 — Presence-aware gating** | Read back the user's presence before writing; never clobber meetings/calls/DND | None in practice (docs table says `Presence.Read`; app already reads with `Presence.ReadWrite` in production — add `Presence.Read` at the same re-consent to be doc-safe) | **None.** Every tool blindly overwrites |
| **P3 — Tray remote** | Play/pause/next/prev + device picker + queue peek from the tray | `user-modify-playback-state` (devices + queue need **no new scope**) | Slack `/spotify` (not approved, Slack-only); nothing combines control with Teams status |
| **P4 — Trust** | Encrypted `tokens.json` (#140), deep-link hijack fix (#66), deadlock fix (#180) | — | — |
| **P5 — Auto-update** | tauri-plugin-updater; ends manual re-downloads | — | — |
| **P6 — Flavor** | Track-change notifications (plugin already installed, dormant), recently-played fallback, album art | `user-read-recently-played` (optional) | — |

**Two corrections the research made to the prior hypothesis:**
1. **`setPresence` only documents `POST /users/{id}/presence/setPresence`** — no `/me` variant (community reports 404s on `/me/presence/setPresence`). The app must resolve the user's Graph object ID, which needs the `profile` scope added to the Teams device-code consent (`teams.rs:148`) so the access token carries the `oid` claim. So P1 causes a **Teams re-consent** anyway — zero-new-*permission* but not zero-new-*consent*.
2. **`setPresence` accepts only five availability/activity combinations** — `Available/Available`, `Busy/InACall`, `Busy/InAConferenceCall`, `Away/Away`, `DoNotDisturb/Presenting`. "Busy" is only representable as "In a call". This is a product-design decision, not an implementation one (see §7).

**Tauri 3.0 is not released** (core milestone "Draft (not ready)", 31% complete; only `tauri-cef` v3 alpha tags exist; stable is v2.11.5). PresenceJam 3.0 targets **Tauri 2.x**; re-evaluate the Tauri-3 cutover only after a Tauri 3 stable is announced.

## 2. The case: the field is empty

Research summary (full matrix in R5):

- **Microsoft Teams has no native Spotify integration** — no app in the Teams store, no status-sync capability. The only route to a Teams status message from Spotify is a DIY Power Automate flow against **undocumented** `presence.teams.microsoft.com/v1/me/publishnote` endpoints (5-min recurrence, daily flow limits, "should not be used in production").
- **Zapier/IFTTT/Make/n8n cannot write the Teams status message at all** — their Teams actions are channel posts, or availability-only ("Set Status"). MS Q&A confirms the presence-vs-message API confusion.
- **Slack tools are a mature but separate market** (SpotMyStatus, Now Playing, DC Music Status — all hosted SaaS, status-message only, subscriptions). Slack has no built-in Spotify integration either.
- **Discord's official integration is status-message only** and hard-locked to the local desktop client.
- **PresenceJam is the only tool using the documented** `POST /users/{id}/presence/setStatusMessage` (Graph, `Presence.ReadWrite`, `expiryDateTime`).

So the 3.0 pillars — availability sync, presence-aware gating, tray remote + Teams status in one local app — have **zero overlap** in the current landscape. The product is alone in a space it can define.

## 3. Pillars, grounded

### 3.1 P1 — Availability sync (`setPresence` / `clearPresence`)

**API contract** (learn.microsoft.com/graph/api/presence-setpresence, presence-clearpresence, cloud-communications-manage-presence-state):

- `POST /users/{id}/presence/setPresence` — body:
  ```json
  { "sessionId": "<app client id>", "availability": "Busy", "activity": "InACall", "expirationDuration": "PT1H" }
  ```
  - `sessionId` **must be the Azure AD application (client) ID** of the app registration — for PresenceJam that's the existing `MICROSOFT_GRAPH_CLIENT_ID` const (`teams.rs:6`). Stable per app; same value on every set and on clear.
  - `expirationDuration`: ISO-8601 duration, **PT5M–PT4H, default PT5M**. Always send it.
  - Valid combos (only these): `Available/Available`, `Busy/InACall`, `Busy/InAConferenceCall`, `Away/Away`, `DoNotDisturb/Presenting`. PascalCase exactly.
  - Response 200 empty. Permissions: delegated least = `Presence.ReadWrite` (verbatim table), no higher option. **Zero new permission — confirmed.**
- `POST /users/{id}/presence/clearPresence` — body `{ "sessionId": ... }`; 200 OK, or **404 NotFound when the session doesn't exist (treat as success)**. Clearing the only session drops the user to `Offline/Offline`.
- **Sessions model:** the app's session is keyed by (user, sessionId). Precedence: user-preferred > session-level; among sessions DND > Busy > Available > Away. **An app session cannot override a user's manual DND** — safe by construction.
- **Timeout/fade:** an `Available/Available` session **fades after 5 minutes** (→ `Available/AvailableInactive`, then `Away/Away` after another 5) *regardless of* `expirationDuration`. Holding "Available" means re-calling setPresence every <5 min. Non-Available states persist until `expirationDuration` expiry, then the session goes `Offline`.
- **Propagation:** Teams polls presence — "takes a few minutes" to update the bubble. Status message is the real-time channel; availability is the ambient channel.
- **`/users/{id}` only, no `/me`:** resolve the Graph object ID via the `oid` claim — add `profile` to the device-code scope string (`teams.rs:148`); the token then carries `oid` (claims reference). (`openid` + `GET graph.microsoft.com/oidc/userinfo` is the alternative; `GET /me` would need `User.Read`, deliberately dropped.) **Try `/me/presence/setPresence` first and fall back to `/users/{oid}` on 404** — `/me` works for `setStatusMessage` today, so support is endpoint-specific [INFERENCE].
- **Error mapping:** reuse the existing `TeamsApiError` discrimination from `post_status_message` (`teams.rs:466-518`) and `parse_retry_after` (`teams.rs:238-244`). Graph documents 429 + `Retry-After`; match on `error.code`, never `message` text.
- **Rate limits:** getPresence 1,500 req/30s/app/tenant; presence service limit 10,000 req/30s/app/tenant. A 30–300 s re-arm loop is trivially inside both.
- **National clouds:** entire presence surface (`setPresence`, `clearPresence`, `getPresence`, `setStatusMessage`) is **unsupported in China (21Vianet)** — extends the existing STATE-OF-FEATURES caveat. Stay on **v1.0** (beta `setPresence` is *more* restricted: GCC L4/L5 ❌).
- **Do NOT use `setUserPreferredPresence`** for this feature: it overrides the user's own manual state (including their DND), only takes effect while a session exists, and has 1–7 day expiry.

**Repo integration (R6 anchors):** new `set_teams_presence`/`clear_teams_presence` fns in `teams.rs` beside `post_status_message`; hook into `process_track` (`poll_once.rs:492-697`, inside the `if let Some(teams_tok)` block at :564) and `handle_no_track` (`:700-757`) gated on a new `TeamsConfig` flag; new config fields follow the exact house pattern (`config.rs` `TeamsConfig` struct :29-36, default fns :57-88, `Default` impl :159-167, ts-rs auto-export, manual mirror in `src/lib/stores/config.ts:20-25` + `:47-53`). **Caveat:** `handle_no_track` reads teams tokens without refresh (`:718-721`) — presence calls there must tolerate a stale token or reuse the fetched one.

### 3.2 P2 — Presence-aware gating (`getPresence`)

- `GET /me/presence` is **documented** (learn.microsoft.com/graph/api/presence-get) and the app already calls it in `validate_teams_token` (`teams.rs:591-628`). Response: `{ activity, availability, id, outOfOfficeSettings, sequenceNumber, statusMessage, workLocation }`. Parse `activity`/`availability` **case-insensitively** (docs enum is lowercase; examples return PascalCase); accept `AvailableInactive` (a fade state absent from the enum).
- **Permission nuance (verified):** the docs table lists delegated least = `Presence.Read`, higher = `Presence.Read.All` — `Presence.ReadWrite` is **not listed**. But `Presence.ReadWrite`'s own description includes "read the presence information", and the app ships v2.8.0 calling `GET /me/presence` with only `Presence.ReadWrite`. **Plan: implement against the current scope; add `Presence.Read` to the Teams scope string at the same re-consent P1 forces anyway, to be doc-safe.** Verify with a live call before shipping.
- **Meeting detection is free.** "In a meeting" is automatically reflected in presence during scheduled calendar meetings (documented); `getPresence` returns `availability=busy, activity=inAMeeting`. OOF is surfaced via `outOfOfficeSettings.isOutOfOffice`. **No calendar API needed for v1** — `Calendars.ReadBasic` + `calendarView` parsing is a deferred enhancement only if meeting-lag complaints justify it.
- **Gate design:** on track change only (not every poll), GET presence; if `availability ∈ {busy, doNotDisturb}` or `activity ∈ {inAMeeting, inACall, presenting}` → **skip the status write**, remember the pending track, restore when presence clears. Emit a `presence-gated` event so the Dashboard can show "suppressed during meeting".

### 3.3 P3 — Tray remote, devices, queue

**New scope:** `user-modify-playback-state` (`commands/spotify_auth.rs:23`). Everything in the table is documented as Premium-only, 204/401/403/429:

| Action | Endpoint |
|---|---|
| Start/Resume | `PUT /v1/me/player/play` |
| Pause | `PUT /v1/me/player/pause` |
| Next / Previous | `POST /v1/me/player/next` / `POST /v1/me/player/previous` |
| Seek | `PUT /v1/me/player/seek?position_ms=` |
| Volume | `PUT /v1/me/player/volume?volume_percent=` (0–100) |
| Shuffle / Repeat | `PUT /v1/me/player/shuffle?state=` / `PUT /v1/me/player/repeat?state=track\|context\|off` |
| Transfer | `PUT /v1/me/player` body `{device_ids: [id], play: bool}` (only ONE id — more → 400) |
| Add to queue | `POST /v1/me/player/queue?uri=` (track or episode uri) |

- **No new scope:** `GET /v1/me/player/devices` (`user-read-playback-state` — held) and `GET /v1/me/player/queue` (**both** `user-read-currently-playing` + `user-read-playback-state` — held; the scopes-page link list is buggy, the endpoint reference page is authoritative).
- **Errors:** 404 with `NO_ACTIVE_DEVICE` is *not* in the current docs (only community-confirmed) — handle it as "no device, offer transfer". 403 = Premium restriction [INFERENCE]. 429 carries `Retry-After`. Device IDs are only "persistent to some extent" — refetch, don't cache long-term.
- **Album art:** `item.album.images` is in the response the app already polls — tray art needs zero extra calls. Episodes only appear with `additional_types=episode`; recently-played excludes episodes entirely.
- **Tray integration (R6):** new menu IDs + items in **both** builders (`tray.rs:9-17`, `build_initial_menu` :108, `update_tray_menu` :177); dispatch in `on_menu_event` (:39-75) — either emit an event (pattern of `toggle-pause`) or call `spotify::player_*` fns directly with `state.tokens.spotify()`. New module `commands/playback.rs` per the exact pattern: `const CMD = "[CMD.PLAYBACK]"` (log-tag convention), `pub mod playback;` in `commands/mod.rs:16-22`, registration in `lib.rs:784-792`, **and update the `test_commands_split_groups_present` regression guard** (`commands/mod.rs:29-46`) or CI fails.
- **Scope-add / re-consent mechanics (critical):** docs do not promise a consent screen for returning users (`show_dialog=false` may auto-redirect) — **set `show_dialog=true`** on the 3.0 re-auth to force the screen. The re-auth returns a **new refresh token** (persist it). Spotify refresh tokens now expire **after 6 months** and refreshing does not extend them — the existing `invalid_grant` → re-auth handling (#160, shipped 2.10.0) is now load-bearing, not optional.

### 3.4 P4 — Trust (security debt)

- **#180 (polling self-deadlock, severity high):** `cas_refresh_or_discard` write-guard + `persist_tokens` read-lock self-deadlock on refresh success. **Must land before 3.0 work starts** (2.10.1/2.11). The issue's suggested fix (drop the guard before persisting) matches the repo's existing CAS-discard regression-test pattern (`poll_once.rs:874+`).
- **#140 (tokens.json at rest):** AES-GCM, keychain-stored key, cipher version byte. The repo's migration house style (R4): on-read/on-startup **idempotent one-shots**, best-effort (never fatal, log-and-continue), conflict-safe, dual-slot/version markers, atomic-write invariants preserved (`token_io.rs:155-238` 0600-at-create + fsync + rename + stale-sidecar pre-clear), regression tests where cheap (round-trip + `include_str!` brace-count guards). Precedents: `migrate_legacy_client_secret` (`config.rs:278-379`), keychain dual-slot forward-migration (`keychain.rs:27,34,104-176`), #65 token-storage rewrite (`token_io.rs`). SECURITY.md "Data Storage" (33-105) must be rewritten — **its claims about DPAPI/Keychain encryption are currently false** (plaintext JSON, mode-0600 only); SETUP.md:120-130 repeats the false claim. README:86 is stale ("tauri-plugin-store for tokens").
- **#66 (deep-link hijack):** the full fix (per-launch UUID scheme or one-time secret in the redirect path) is a coordinated Spotify-Dashboard + Tauri-config + handler change. macOS remains the only unfixed platform today; PKCE bounds the impact. Decision needed: fold into 3.0 or defer (it's independent of the feature pillars).

### 3.5 P5 — Auto-update + signing

- **Stack:** `tauri-plugin-updater = "2"` (Rust ≥1.77.2) + `@tauri-apps/plugin-updater`; register in `lib.rs` setup; add `"updater:default"` to `capabilities/default.json`; `bundle.createUpdaterArtifacts: true`; `plugins.updater.pubkey` = **inline key content** (not a path); `plugins.updater.endpoints: ["https://github.com/Carme99/PresenceJam-Desktop/releases/latest/download/latest.json"]`.
- **Keys (one-time):** `npm run tauri signer generate -- -w ~/.tauri/updater.key` (+ password); store private key + password as GitHub Actions secrets `TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (`.env` files are NOT read by the CLI). **Losing the private key permanently blocks updates to installed users.** Pubkey goes into `tauri.conf.json`.
- **Manifest:** `latest.json` requires `version`, `platforms.<os>-<arch>.url`, `platforms.<os>-<arch>.signature` (**signature = .sig file content**). No native GitHub auto-discovery — either switch the release job to `tauri-apps/tauri-action@v1` (`uploadUpdaterJson: true` generates it) or hand-assemble after the release is created and `gh release upload` it. Sequencing: release job already `needs: build` — correct shape.
- **Artifacts:** macOS `PresenceJam.app.tar.gz` + `.sig`; Windows the MSI + `.msi.sig`; Linux AppImage + `.AppImage.sig`. Packaging steps in `release.yml` (build matrix) must copy/upload these.
- **UX:** no built-in prompt — ship a small update dialog (`check()` on startup → banner → `downloadAndInstall()` → `relaunch()`). Major transitions (2.10 → 3.0) ride the updater cleanly (plain semver comparison).
- **Signing:** updater payload signing (minisign `.sig`) is independent of OS signing and **works on unsigned builds**. macOS unsigned keeps the right-click→Open Gatekeeper story (also for the updated .app); Windows unsigned keeps SmartScreen warnings. Full OS signing options: Apple Developer Program **$99/yr** (Developer ID + notarization via App Store Connect API keys); Windows OV cert ~$200–500/yr or **Azure Artifact Signing ~$10/mo** (Basic tier, 5k sigs). Linux needs none.
- **Gap to flag:** the matrix builds **aarch64 macOS only** (`release.yml:17`) — Intel Macs would silently never get updates. Adding x86_64/universal macOS is a release-matrix change worth bundling with P5.
- **Tauri 3.0:** not released; **do not wait** (see §1).

### 3.6 P6 — Flavor

- **Track-change notifications:** `tauri-plugin-notification` is already registered (`lib.rs:537`) and in `package.json`, but **never used in `src/`** (grep: zero matches) and **no `notification:default` capability** — add the capability + a `Dashboard.svelte:53-65` listener (`spotify-track-changed`), gate on `isPermissionGranted`/`requestPermission`, `sendNotification({title, body, icon: album_art_url})` (CSP already allows `i.scdn.co`). Zero Rust changes.
- **Recently-played fallback** ("Last listened: X" when paused): needs `user-read-recently-played` (tracks only, `?limit=50`, `played_at`); a third scope → decide if the extra consent is worth it.
- **Tray polish:** album art + queue peek (up to 2-3 upcoming) in the tray tooltip; `is_private_session`/`is_restricted`/`supports_volume` badges; explicit badge.

## 4. Breaking-change ledger (why this is a *major*)

| Change | Impact on existing users |
|---|---|
| Teams re-consent (`profile` + `Presence.Read` added) | One device-code re-auth for everyone; **nothing forces it today** — must add a version-gated reconnect prompt or new endpoints 403 for stale tokens |
| Spotify re-consent (`user-modify-playback-state` added) | One PKCE re-auth for everyone (with `show_dialog=true`); new refresh token persisted; 6-month lifetime restarts |
| `tokens.json` format (encrypted, cipher version byte) | One-way migration; old binaries cannot read the new format → major-version justification on its own |
| Config schema additions | Non-breaking by serde default; only additive |
| New `Breaking` CHANGELOG section | First in repo history — precedent for future majors |

## 5. Implementation plan (phased, each phase = green gates then commit)

Orchestration pattern per repo convention (worktree-per-branch, contract-first, verifier-before-merge, dependency-ordered merging — `presencejam-fix-orchestration`): every phase ships as its own PR; the two type-coupled paths (ts-rs codegen + frontend, Rust scope change + reconnect UX) merge in dependency order.

**Phase 0 — pre-3.0 bugfix (2.10.1 or 2.11):**
1. #180 deadlock fix + regression test (`poll_once.rs`).
2. #182 winget CI fix (WINGET_TOKEN CreateRef permission).
Ship and tag before any 3.0 work. Never build 3.0 on a known polling-thread hang.

**Phase 1 — P4a: encrypted tokens.json (#140).**
`token_io.rs` AES-GCM + keychain key + version byte + plaintext→ciphertext migration; SECURITY.md/SETUP.md doc sweep for the false DPAPI claims. Foundational (changes the file format 3.0 migrations depend on).

**Phase 2 — P3 backend:** `spotify.rs` `player_*` fns, `commands/playback.rs`, tray IDs + both builders + dispatch, `test_commands_split_groups_present` update, `SPOTIFY_SCOPES` + `user-modify-playback-state`, scope-gated reconnect prompt (Settings/Dashboard banner for stale tokens → 403-driven or version-gated).

**Phase 3 — P1 + P2:** `teams.rs` `set_teams_presence`/`clear_teams_presence`/`get_teams_presence`, `oid` resolution, Teams scope string (`profile` + `Presence.Read`), `poll_once.rs` hooks + `presence-gated`/`presence-availability-updated` events, `TeamsConfig` fields (availability mode, gate toggle), Settings Presence/Availability section, Dashboard badges. Both re-consents land here — one upgrade moment.

**Phase 4 — P5 updater:** plugin, capabilities, signer keys (one-time, human step), `latest.json` wiring (tauri-action switch or hand-rolled), update-prompt UI, release.yml packaging + uploads, optional x86_64 macOS matrix entry.

**Phase 5 — P6 flavor:** notifications capability + Dashboard listener; album art/queue tray polish; (optional) recently-played.

**Phase 6 — release cut:** docs sweep (SECURITY/SETUP/README/STATE-OF-FEATURES/TROUBLESHOOTING/USAGE), CHANGELOG `## [3.0.0]` with a **Breaking** section, version bump (5 sites: package.json, package-lock.json, Cargo.toml, Cargo.lock, tauri.conf.json), merge, tag `v3.0.0` at the merge commit, watch release.yml, verify updater loop on a dev machine (3.0.0 → a 3.0.1 patch proves it).

## 6. Release mechanics for a major (from `release-flow-pr-merge-version-bump-tag`)

- Version bump = **5 sites** (package.json, package-lock.json via `npm install`, Cargo.toml, Cargo.lock via `cargo update -p presence-jam --offline`, tauri.conf.json) + CHANGELOG. Sweep-verify with a grep for the old version.
- Tag must point at the **version-bump PR's merge commit** on main — never a local pre-merge commit (irreversible).
- New for 3.0: the `TAURI_SIGNING_PRIVATE_KEY` env must be present in **every** build-matrix job; `latest.json` must be an asset of the stable (non-draft, non-prerelease) release; keep `digest-mismatch: warn` until one clean cycle.
- Post-cut verification checklist: install MSI/DMG/AppImage → check() → update to a follow-up patch → relaunch; `curl .../releases/latest/download/latest.json` returns all platforms with valid signatures.

## 7. Decisions needed from the maintainer

1. **Availability semantics (P1):** "Busy" only exists as `Busy/InACall` / `Busy/InAConferenceCall` — showing "In a call" to colleagues while listening to music may be misleading. Options: (a) availability sync **off by default**, opt-in; (b) use `Available/Available` (re-armed <5 min) as "listening but available"; (c) only sync on pause/stop (clear → Available) and never claim Busy. **Recommendation: (a), with (b) as the "listening" state if enabled.**
2. **Signing budget:** auto-update works unsigned (SmartScreen/Gatekeeper story unchanged), but P5's polish depends on $99/yr (Apple) + ~$10/mo (Azure Artifact Signing) or ~$200–500/yr (OV). Decide before Phase 4.
3. **Scope cut:** P1+P2 are the 3.0-defining pillars (both force the Teams re-consent — do them together). P3 forces the Spotify re-consent. P4 (#140) and P5 are infrastructure. P6 is optional. Minimum credible 3.0: P1+P2+P4a; recommended: P1+P2+P3+P4a+P5.
4. **macOS x86_64:** add a matrix entry when P5 ships, or Intel users silently get no updates.
5. **#66 deep-link:** fold into 3.0 (coordinated Spotify-Dashboard change) or keep as a tracked macOS gap.
