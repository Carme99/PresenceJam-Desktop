## Bug-Level Issues (fix before release)

### B1: `refresh_teams_token` silently drops refresh token on rotation
**File:** `src-tauri/src/teams.rs:304-314`  
**Severity:** HIGH  
**Impact:** After first refresh, subsequent refreshes fail permanently, requiring re-auth.

Microsoft's token endpoint doesn't always return a new `refresh_token`. The code at line 313:

```rust
refresh_token: token_resp.refresh_token,
```

Looking at the `TokenResponse` struct (line 87), `refresh_token` is `Option<String>`. If the response omits it, `TeamsTokens.refresh_token` becomes `None`. On the next refresh cycle, line 290:

```rust
let refresh_token = tokens.refresh_token.as_ref()
    .ok_or("No refresh token available. Please sign in again.")?;
```

This hard-fails. The fix applied in `spotify.rs:163` (`unwrap_or_else(|| tokens.refresh_token.clone())`) was never ported to Teams.

**Fix:** Mirror the Spotify pattern:
```rust
refresh_token: token_resp.refresh_token
    .or_else(|| tokens.refresh_token.clone()),
```

### B2: `atomic_write_json` is not atomic on Windows
**File:** `src-tauri/src/config.rs:258-271`  
**Severity:** HIGH on Windows, LOW on Unix  
**Impact:** Config corruption if the process crashes between `remove_file` and `rename`.

```rust
if path.exists() {
    std::fs::remove_file(path)?;  // <-- gap here
}
std::fs::rename(&temp_path, path)?;
```

On Unix, `rename()` atomically replaces the destination — the `remove_file` is unnecessary and creates a window where no config file exists. On Windows, `rename` doesn't overwrite, requiring the remove, but the gap is dangerous.

**Fix:** Use `std::fs::rename` directly on Unix. On Windows, use a backup-then-rename approach or `fs::rename` with retry. Better yet, use the `tempfile` crate which handles this cross-platform.

### B3: Dead code — `Credentials` struct and `load_credentials`/`save_credentials`
**File:** `src-tauri/src/config.rs:192-323`  
**Severity:** LOW  
**Impact:** Dead code — 132 lines never called. `load_credentials` and `save_credentials` have zero callers outside their own definitions. The app uses `tauri-plugin-store` for token persistence instead.

**Fix:** Remove the `Credentials` struct, `load_credentials()`, `save_credentials()`, and tests for them. Reduces compile time and maintenance surface.

### B4: Dead code — `spotify::start_spotify_auth()` 
**File:** `src-tauri/src/spotify.rs:56-83`  
**Severity:** LOW  
**Impact:** Function exists but no caller. The Tauri command `start_spotify_auth` in commands.rs generates its own verifier/challenge/state directly rather than calling this function. The function also has a confusing return type — it returns `(challenge, verifier)` but the `challenge` is the SHA256 hash which no caller needs.

**Fix:** Either remove the function (preferred — the command does more than the function offers) or refactor the command to use it. The inconsistency between the two implementations (different PKCE generation paths) is a maintenance hazard.

### B5: Config defaults out of sync between TypeScript and Rust
**File:** `src/lib/stores/config.ts:56` vs `src-tauri/src/config.rs:77`  
**Severity:** MEDIUM  
**Impact:** TypeScript default for `minimum_interval_seconds` is 10, Rust default is 5. The code has a comment: *"This default is only used if load_config fails. Both must stay in sync manually."* — they're not in sync. If loadConfig fails on a fresh install, the UI shows 10s minimum but the Rust default would be 5s on next save.

**Fix:** Pick one value (5 or 10) and align both. Given polling uses hardcoded MINIMUM = 10 in polling.rs, 10 is the practical minimum. Change Rust default to 10 or document the discrepancy.

### B6: Manual URL paste handler silently swallows errors

} catch (e) {

## UX & Polish Issues

### U1: Tray menu double separator when no track playing
**File:** `src-tauri/src/tray.rs:230-260`  
**Severity:** LOW  
**Impact:** When no track is playing, the tray menu shows two separators sandwiching the Settings/Logs section:
```
Show Window
Pause Sync
───────────    ← separator1
Open Settings
Open Logs Folder
───────────    ← separator3 (redundant)
Quit
```

The `separator1` is always placed before the track section, and `separator3` always after. When there's no track, they visually double up.

**Fix:** Only include `separator1` when a track is being displayed. Or merge into a single separator section.

### U2: `About.svelte` has stale hardcoded version fallback
**File:** `src/lib/components/About.svelte:3` and `src/routes/+page.svelte:14`  
**Severity:** LOW  
**Impact:** `const BUILD = import.meta.env.__APP_BUILD__ || '2.4.1.unknown';` — the fallback `2.4.1` is stale (should be 2.4.2) and will drift on every release. Also duplicated in two files.

**Fix:** Extract to a shared constant or always read from the build define. Fix the fallback to match current version or use a generic `'unknown'`.

### U3: `User-Agent` hardcoded to `PresenceJam/2.0`
**File:** `src-tauri/src/teams.rs:30`  
**Severity:** LOW  
**Impact:** All Teams HTTP requests identify as version 2.0 when the app is 2.4.2. Minor but inaccurate.

**Fix:** Read version from `env!("CARGO_PKG_VERSION")` at build time:
```rust
.user_agent(format!("PresenceJam/{}", env!("CARGO_PKG_VERSION")))
```

### U4: Quit handler in menu.rs silently discards exit failure
**File:** `src-tauri/src/menu.rs:124`  
**Severity:** LOW  
**Impact:** If the fallback `exit(0)` fails after 500ms, the app stays open with no log or user feedback. This is the second-chance path (normal shutdown via `app-shutdown` event should exit cleanly), but silent failure is poor.

**Fix:**
```rust
if let Err(e) = app_handle.exit(0) {
    log::error!("[MENU] quit: forced exit failed: {}", e);
}
```

**Fix:** Add a startup task that deletes log files older than `retention_days`. Or use `tauri-plugin-log`'s rotation feature if available.

## Code Quality Issues

### C1: Tray menu `update_tray_menu` has fragile error handling
**File:** `src-tauri/src/tray.rs:169-260`  
**Severity:** MEDIUM  
**Impact:** Every menu item builder uses `.map_err(|e| { log::warn!(...); e.to_string() })?` — if any single item fails to build, the entire tray menu update is aborted. Users get a stuck/stale tray menu with no indication something is wrong other than a log line.

**Fix:** Build all items, collect errors, build what you can, log what failed. A partial menu is better than a stale one.

### C2: `Dashboard.svelte` has race between `sync-started`/`sync-stopped` and menu state
**File:** `src/lib/components/Dashboard.svelte:105-118`  
**Severity:** LOW (already flagged in batch review as W5)  
**Impact:** `updateMenuState()` is called without `await` in event listeners. Out-of-order resolution possible.

**Fix:** Add `await` or add a sequence counter.

---

### C3: `saveConfig` can produce out-of-order writes
**File:** `src/lib/stores/config.ts:96-108`  
**Severity:** LOW  
**Impact:** If `saveConfig(A)` is called while `saveConfig(B)` is in progress, the second call awaits the first, then starts a NEW save with `B`. But if during the wait, state changed back to `A`, the second save may overwrite `B` with `A` (stale data). The `savePromise` serializes execution but doesn't capture the latest intended state.

**Fix:** Use a queue or track the latest requested config:
```typescript
let pendingConfig: AppConfig | null = null;
// In saveConfig: set pendingConfig = cfg, then after previous save, save the latest pendingConfig
```

---

### C4: `poll_teams_auth` spawns without cancellation support
**File:** `src/lib/components/Onboarding.svelte:211-230`  
**Severity:** LOW  
**Impact:** Clicking "I've completed sign-in" calls `invoke('poll_teams_auth')` which blocks until the Rust function returns (up to 15 minutes). If the user closes the window or navigates away, the Rust thread keeps polling but the frontend lost its event listener. This is benign (the Rust function eventually times out) but wasteful.

**Fix:** Pass a cancellation token or timeout from the frontend. Unlikely to cause user-visible problems given the 15-minute device code window.

## Architecture & Maintainability

### A1: Polling config fields are dead code in the polling loop
**File:** `src-tauri/src/config.rs:64-69` (definition) vs `src-tauri/src/polling.rs:19-20` (usage)  
**Severity:** MEDIUM  
**Impact:** `PollingConfig.minimum_interval_seconds`, `max_interval_seconds`, and `default_interval_seconds` are stored in config, surfaced in the UI, and serialised — but the polling loop uses hardcoded `const` values instead:

```rust
// polling.rs - never reads config
const MINIMUM_INTERVAL_SECONDS: u64 = 10;
const MAX_INTERVAL_SECONDS: u64 = 60;
```

The config's minimum of 5 is lower than the engine's minimum of 10 — user thinks they can set 5s polling but the engine enforces 10s. This is a design mismatch.

**Fix:** Either read from config in the polling loop (with validation), or remove the config fields and use consts everywhere. Reading from config gives users control over polling behaviour. If removing, update the UI slider to use consts directly.

---

### A2: No config version/migration
**File:** `src-tauri/src/config.rs:113-120`  
**Severity:** MEDIUM  
**Impact:** `AppConfig` has no version field. If the config schema changes between releases, old configs silently fail to parse (all fields become defaults). Users lose their settings. Adding a new required field would break all existing configs.

**Fix:** Add `version: u32` or `schema_version: String` to AppConfig. On load, check version and run migration functions. Even a `version: 1` field that does nothing today establishes the pattern.

---

### A3: `commands.rs` at 1117 lines
**Severity:** LOW  
**Impact:** All 19 Tauri commands in one file. Navigation pain as the app grows. File has no clear section dividers.

**Fix:** Split into `commands/auth.rs`, `commands/polling.rs`, `commands/config.rs`, `commands/ui.rs` by domain. Low priority for solo dev but worth doing before the file passes 1500 lines.

---

### A4: `teams.rs` dual implementation of `set_teams_status_message` and `clear_teams_status_message`
**Severity:** LOW  
**Impact:** These are identical functions with different names: both POST to `setStatusMessage` with a content string. `clear_teams_status_message` just passes `expiry_date_time: None`. The duplication means:
- `clear_teams_status_message` doesn't actually "clear" anything — it sets a status message with empty/placeholder text
- If the Graph API changes, two functions need updating
- The naming is misleading

**Fix:** Unify into a single function `set_teams_status_message_content(content: &str, expiry: Option<&str>)`. If actual presence clearing is needed, use a different Graph endpoint.
